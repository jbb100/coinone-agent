# 코인원 거래 로직 전면 리뷰 (2026-07)

> 리뷰 배경: "하락장에 오히려 많이 수집하고 상승장에 많이 팔아야 맞는 것 아닌가?"라는 문제 제기에 따라
> KAIROS-1의 매수/매도 의사결정 로직 전체를 검토한 결과입니다.

## 요약 (TL;DR)

1. **최상위 배분 로직(시장 계절 필터)은 역발상이 아니라 추세추종입니다.**
   강세장(BTC > 200주 MA × 1.05)에 암호화폐 70%, 약세장(< × 0.95)에 30%로,
   *가격이 오른 뒤에 사고, 내린 뒤에 파는* 구조입니다. 문제 제기하신 방향과 정반대입니다.
2. **하위 전략(DCA+, 기회적 매수)은 정확히 반대 철학(역발상 매집)으로 만들어져 있어
   두 층이 서로 싸웁니다.** 약세장에서 기회적 매수가 사들인 물량을 다음 리밸런싱이 도로 팝니다.
3. **상승장 매도(익절) 모듈은 존재하지 않습니다.** 기회적 "매수" 시스템만 있고 대칭되는
   기회적 "매도" 시스템이 없습니다.
4. 그와 별개로, **데이터 장애 시 무조건 강세장(RISK_ON)으로 판정되는 fail-unsafe 기본값**,
   **완충 밴드 히스테리시스 미작동**, **DCA 월 한도 계산 오류** 등 실제 손실로 이어질 수 있는
   버그가 다수 발견되었습니다.

## 1. 질문에 대한 직접 답변: 이 시스템은 "하락장 매집"을 하는가?

### 1.1 계층별로 방향이 다릅니다

| 계층 | 모듈 | 하락장 행동 | 상승장 행동 | 철학 |
|---|---|---|---|---|
| 최상위 (자산배분) | `MarketSeasonFilter` + `Rebalancer` | 암호화폐 70→30%로 **매도** | 30→70%로 **매수** | 추세추종 |
| 중간 (적립식) | `DCAPlus` | 공포 시 최대 3배 **증액 매수** | 탐욕 시 0.3배 축소 | 역발상 |
| 하위 (현금활용) | `OpportunisticBuyer` | 급락 시 현금의 최대 50% **추가 매수** | 아무것도 안 함 | 역발상 |
| 익절 | (없음) | — | — | — |

최종 포지션을 지배하는 것은 최상위 배분(40%p 스윙)이므로, **시스템 전체로는
"하락 후 매도, 상승 후 매수"가 맞습니다.** 하위 전략의 역발상 매수는 규모가 작고,
리밸런싱이 결국 목표 비중으로 되돌립니다.

### 1.2 추세추종 자체가 틀린 것은 아니지만, 기준선이 잘못되었습니다

추세추종 국면 필터(가격이 추세선 아래면 위험 축소)는 2018·2022 같은 깊은 하락을
회피하는 검증된 접근입니다. 다만 **200주 이동평균선은 이 용도에 부적합합니다**:

- BTC 역사상 200주 MA 아래 구간(2015, 2018-19 저점, 2020.3, 2022 말)은 모두
  **사이클 바닥 = 역사적 최고의 매집 구간**이었습니다.
- 즉 현재 로직은 *역사적으로 가장 싼 구간에서 암호화폐를 30%까지 팔고*,
  가격이 200주 MA × 1.05를 회복한 뒤(이미 바닥 대비 크게 오른 뒤) 70%까지 되삽니다.
- 추세추종을 하려면 20주/50주 MA처럼 반응이 빠른 선을 쓰는 것이 정석이고,
  200주 MA는 오히려 "이 아래에서는 절대 팔지 않는 가치 바닥"으로 쓰는 것이
  일반적입니다. **문제 제기하신 직관("바닥권에서 팔면 안 된다")은 이 기준선에 한해서는
  타당합니다.**

흥미롭게도 `DCAPlus._calculate_accumulation_score()`는 이미 "200주 MA 대비 -25% 이하 =
최강 매집 신호"로 정의하고 있어(`dca_plus_strategy.py:118, 505`), **같은 코드베이스 안에서
200주 MA 하회를 한쪽은 '매도 신호', 다른 쪽은 '최강 매수 신호'로 해석**하고 있습니다.
이것이 이 시스템의 가장 근본적인 전략 모순입니다.

### 1.3 상승장 매도가 없다

- `take_profit`은 파라미터만 존재하고 항상 `None`으로 전달됩니다 (`rebalancer.py:1201`).
- `OpportunisticBuyer`에 대칭되는 매도 모듈(과열/탐욕 시 단계적 익절)이 없습니다.
- 상승장에서 실제로 파는 유일한 메커니즘은 "목표 비중 초과분 리밸런싱 트림"인데,
  RISK_ON 진입 시 목표 자체가 70%로 올라가므로 트림이 아니라 순매수가 됩니다.

## 2. 전략 계층 간 충돌 시나리오 (실제 발생 가능)

**약세장 진입 시:**
1. 주간 분석: RISK_OFF 판정 → 리밸런서가 암호화폐를 30%까지 매도.
2. 같은 주에 `OpportunisticBuyer`가 급락(-10%)·RSI 과매도 감지 → 현금의 20~50% 매수.
3. `DCAPlus`도 공포지수 기반 2~3배 증액 매수.
4. 다음 리밸런싱 사이클: 비중이 30%를 초과했으므로 **방금 산 물량을 다시 매도.**
5. 결과: 수수료(왕복 ~0.2%) + 세금 이벤트 + 슬리피지만 남고 포지션은 제자리.

조정자(arbiter)가 없어서 각 모듈이 서로의 결정을 모른 채 반대 매매를 합니다.
`multi_rebalancing_engine`, `system_coordinator`가 있지만 이 충돌을 중재하는 로직은 없습니다.

## 3. 발견된 버그 (심각도순)

### 🔴 P0 — 데이터 장애 시 무조건 "강세장" 판정 (fail-unsafe)

1. **`rebalancer.py:901`** — 200주 MA 계산 실패 시
   `ma_200w = current_price * MA_CALCULATION_FALLBACK_RATIO(0.9)`.
   → price_ratio가 항상 1/0.9 = **1.111 ≥ 1.05 → 무조건 RISK_ON**.
   데이터 API가 죽으면 시스템이 "강세장"으로 판단하고 암호화폐 70%까지 매수합니다.
2. **`market_season_filter.py:55,61,67,109`** — 가격 데이터 부재 시 MA 기본값
   **5,000만 원 하드코딩**. 현재 BTC 가격 기준으로 ratio가 수 배가 되어 역시 강제 RISK_ON.
3. **`rebalancer.py:937,941`** — BTC USD 가격 조회 실패 시 **$50,000 하드코딩** →
   환산된 200주 MA가 왜곡되어 계절 오판.

**세 경우 모두 "실패 시 NEUTRAL(또는 직전 상태 유지) + 알림 + 거래 중단"이어야 합니다.**
장애가 매수 신호로 변환되는 현재 구조는 가장 먼저 고쳐야 합니다.

### 🔴 P0 — 완충 밴드 히스테리시스 미작동

`determine_market_season()`은 밴드 내(0.95~1.05)일 때 `previous_season`을 유지하도록
설계되었지만, 실제 호출부는 전부 `previous_season=None`을 넘깁니다:
- `market_season_filter.py:223` (`analyze_weekly`)
- `rebalancer.py:905-909` (실시간 판단)

→ 밴드 내에서는 항상 NEUTRAL(50:50)로 떨어집니다. ratio가 1.06 → 1.04 → 1.06으로
움직이면 70% → 50%(20%p 매도) → 70%(20%p 매수)를 반복합니다. **밴드가 막으려던
휩쏘를 밴드 자신이 만들어냅니다.** DB에 저장된 직전 계절을 읽어 넘겨야 합니다.

또한 README는 밴드 내 "기존 비중 유지"라고 문서화했지만 코드는 NEUTRAL=50:50
강제 배분입니다 (`market_season_filter.py:194-197`). 문서와 코드 중 하나는 틀렸습니다.

### 🟠 P1 — DCA+ 월 투자 한도 계산 오류

`dca_plus_strategy.py:287-298`:
```python
base_amount = schedule.base_amount_krw * (frequency_days / 30)  # 주간 금액
monthly_total = base_amount * overall_multiplier                 # ← 주간 금액임
if monthly_total > schedule.max_monthly_amount: ...
```
주간 집행액을 **월 한도와 직접 비교**하므로, 실제 월 지출은 한도의 최대 ~4.3배까지
허용됩니다. 월 누적 집행액을 추적해서 비교해야 합니다.

### 🟠 P1 — 기회적 매수의 "하락률"이 하락률이 아님

`opportunistic_buyer.py:179-180` — `price_drop_7d = 현재가/7일평균 - 1`.
고점 대비가 아니라 **평균 대비**라서, 완만한 지속 하락장에서는 4시간 간격
(`min_buy_interval_hours=4`)으로 계속 트리거됩니다. 떨어지는 칼날에 현금을
연속 투입하는 구조입니다. 여기에:
- `opportunity_thresholds`의 EXTREME(-30%)은 7일 "평균 대비"로는 사실상 도달 불가 →
  레벨 체계가 의도대로 동작 안 함.
- `opportunistic_buyer.py:424` — `final_quantity = max(min_limit, ...)`이 예산보다
  **큰 수량으로 상향 조정**될 수 있음 (예산 5천 원어치인데 최소수량이 그 이상이면 그대로 매수).
- `recent_buys`가 메모리 전용이라 프로세스 재시작 시 중복매수 방지가 초기화됨
  (`opportunistic_buyer.py:90`).

### 🟠 P1 — 공포탐욕지수가 실제 지수가 아님

- `opportunistic_buyer.py:127-142`: alternative.me 연동이라 문서화되어 있으나 실제로는
  7일 변동성 기반 자체 근사치.
- `dca_plus_strategy.py:364-377`: RSI로 추정.
- 두 근사치의 스케일·구간 기준(≤40 vs 26-45)도 서로 다릅니다.
README의 "공포탐욕 지수 연동"은 현재 사실이 아니며, 두 모듈이 같은 이름의 다른 지표로
반대 방향 결정을 내릴 수 있습니다.

### 🟡 P2 — 프로덕션 클래스에 목(mock) 메서드 혼재

`rebalancer.py`의 `full_rebalancing_cycle()`, `run_rebalancing_cycle()`(360-387행)은
**아무것도 실행하지 않고 `success: True`를 반환**합니다. `generate_rebalancing_plan()`도
빈 trades를 반환합니다. 스케줄러가 이 메서드를 호출하면 "리밸런싱 성공" 로그만 남고
실제로는 아무 일도 일어나지 않습니다. 테스트 호환용 코드는 테스트 더블로 분리해야 합니다.

### 🟡 P2 — 기타

- `market_season_filter.py:82`: 200주 데이터 부족 시 **200일 MA로 조용히 대체** —
  완전히 다른 국면선이라 판정이 급변합니다. 대체하지 말고 NEUTRAL 처리해야 합니다.
- `constants.py:14` REBALANCE_THRESHOLD=1% vs 각처 기본값 5% — 임계값 이원화.
- `dca_plus_strategy.py:195-199` signal_strength 계산식: 배수(0.8~1.3)를 0-1 점수에
  그대로 가중합산해 스케일이 깨져 있음 (거의 항상 상한 부근).
- `_expand_crypto_orders`(portfolio_manager.py:280-285): core/satellite 70:30을
  가중치에서 다시 계산하지 않고 하드코딩 — `AssetAllocation` 설정과 불일치 가능.

## 4. 권고안

### 4.1 전략 구조 (제기하신 방향을 반영)

**A. 200주 MA의 역할 전환 (권장)**
- 200주 MA **하회 = 매집 구간**: 하회 깊이에 비례해 DCA 증액 + 기회적 매수 예산 확대.
  (이미 `DCAPlus`의 accumulation score가 이 논리를 갖고 있으므로 최상위 배분과 통일)
- 200주 MA 대비 **큰 폭 상회 = 분배 구간**: 예) Mayer Multiple(현재가/200일 MA) 2.4 이상
  또는 200주 MA 대비 +100% 이상에서 단계적 익절 (OpportunisticBuyer와 대칭인
  `OpportunisticSeller` 신설: 과열 레벨별 5단계 매도, 탐욕지수 연동).
- 중간 지대에서는 고정 배분 + 밴드 리밸런싱(이것만으로도 "고점 트림/저점 보충"의
  역발상 효과가 자동으로 발생).

**B. 추세추종을 유지하려면**
- 국면 판정선을 20주/50주 MA로 교체하고, 200주 MA는 "이 아래에서는 매도 금지 +
  기회적 매수 우선"인 가치 바닥으로 사용.

**어느 쪽이든 필수: 단일 조정자(arbiter).**
시장 계절이 자산 비중의 *허용 밴드*(예: RISK_OFF 30~45%)를 정하고, 하위 전략은
그 밴드 안에서만 움직이도록. 기회적 매수분은 N일간 리밸런싱 클로백 면제 태그를 붙여
"사자마자 팔리는" 충돌을 차단.

### 4.2 즉시 수정 (전략 방향과 무관하게)

1. 모든 데이터 실패 fallback을 "NEUTRAL/직전 상태 유지 + 거래 중단 + 알림"으로 변경
   (5천만 원, ×0.9, $50,000 하드코딩 제거).
2. DB의 직전 시장 계절을 `previous_season`으로 전달해 히스테리시스 복구,
   NEUTRAL 의미(50:50 강제 vs 현상 유지)를 문서와 일치시키기.
3. DCA 월 한도를 월 누적 집행액 기준으로 수정.
4. 기회적 매수 하락률 기준을 "N일 고점 대비"로 교체, 수량 상향 클램프 제거,
   `recent_buys` DB 영속화.
5. 실제 공포탐욕지수 API 연동(단일 소스) 또는 근사치임을 명시하고 모듈 간 기준 통일.
6. `Rebalancer`의 mock 메서드를 프로덕션 클래스에서 제거.

### 4.3 검증

  현재 저장소의 비교 리포트(conservative가 샤프 1.99로 1위)는 mock 컴포넌트가 섞인
  데모 결과라 의사결정 근거로 쓰기 어렵습니다.
